AArch64 Type-1 Hypervisor 入门手册：跟着 Xen 学，从零写到 C 世界

第一章：基础概念

1.1 Type-1 与 Type-2

  • Type-1（裸机型） ：hypervisor 直接跑在硬件上，自己就是最小的“操作系统内核”，guest OS 跑在它之上。Xen、Hyper-V 属于这类。
  • Type-2（托管型） ：hypervisor 是一个普通 OS 里的程序/模块，借宿主 OS 管理硬件。VMware Workstation、KVM（从架构上看）属于这类。

本手册讲 Type-1：你的代码是复位后第一批运行的代码，没有 OS 替你铺路，所以“从启动到 C 世界”这段路要自己修。

1.2 ARM 异常级别 EL0–EL3

ARMv8-A 把 CPU 分成 4 个特权级别，数字越大权限越大：

级别 名字 通常住谁 类比
EL0 用户态 普通应用程序 用户
EL1 内核态 guest OS 内核（如 Linux） 操作系统
EL2 虚拟化层 你的 hypervisor 宿主管家
EL3 安全世界/固件 TF-A、Secure Monitor 主板固件
  1. 只有 EL2 才有虚拟化扩展：VTTBR_EL2（Stage-2 页表基址）、HCR_EL2（陷获配置总开关）、VBAR_EL2（EL2 自己的异常向量表）这些寄存器只在 EL2 可访问。
  2. 从高 EL 进低 EL 用 eret（异常返回），低 EL 想叫高 EL 用 svc/hvc/smc（分别进入 EL1/EL2/EL3）。guest 调 hypervisor 就是执行 hvc #0。
  3. EL2 还有两个变体：EL2h / EL2t（由 SPSel 决定用不用专属栈指针 SP_EL2），Xen 两个都接受。

1.3 两段式地址翻译：Stage-1 与 Stage-2

普通 OS 里，虚拟地址（VA）经 MMU 翻译成物理地址（PA）。虚拟化下多了一段：

guest 并不知道 Stage-2 的存在；hypervisor 靠 Stage-2 把每个 guest 限制在各自的内存范围内。Stage-2 是 Type-1 hypervisor 实现隔离的关键机制，本手册第 7 站之后会用到它，但“进 C 世界”之前你不需要建它。

1.4 陷入（trap）与敏感操作拦截

hypervisor 让 guest 以为自己独占硬件，但敏感操作会掉进 EL2，由你拦截。

  • guest 执行 hvc → 硬件自动跳转到 VBAR_EL2 指向的向量表 → 你的代码运行；
  • guest 访问不存在的内存（Stage-2 缺页）→ 产生 Stage-2 Abort → 同样掉进 EL2；
  • guest 开关中断、访问定时器等 → 由 HCR_EL2 的各位决定是否掉进 EL2。

掉进来时，硬件把原因写进 ​ESR_EL2​（异常症状寄存器），你的分发代码读它来分派处理。Xen 里对应 guest_sync → do_trap_guest_sync 这条链。

1.5 两份核心文档

  • ARM ARM（Arm Architecture Reference Manual, ARMv8-A 版，文档号 DDI 0487）：寄存器位定义和异常模型都以它为准。遇到不认识的位段，查它。
  • Linux arm64 booting 文档（Documentation/arch/arm64/booting.rst）：定义了引导器加载你时必须遵守的约定；按它写，U-Boot/GRUB 等引导器才能正确加载。

第二章：Xen 启动的七个阶段

把 Xen 从引导器跳入后的第一条指令到 C 语言入口（start_xen）的整条路分成七个阶段：

2.1 镜像头与加载约定

Xen 的做法（xen/arch/arm/arm64/head.S 开头，节选）：

  1. 引导器跳进 Xen 后执行的第一条指令是 ​​add x13, x18, #0x16​。这条指令本身没有实际作用，它的意义在机器码：前两个字节恰好是 4D 5A，即 ASCII "MZ"——UEFI 要求 PE/COFF 可执行文件以 "MZ" 开头。于是同一个文件头同时满足两种加载器。
  2. b real_start 才是真正干活的跳转。
  3. 后面那一串 .quad/.byte 是 Linux arm64 Image 头：告诉引导器“我是什么格式、希望加载到哪、有多大”。.byte 0x41,0x52,0x4d,0x64 拼出来是 "ARM\x64" magic，引导器靠它确认没加载错文件。

你要学的：不要发明私有镜像格式。照着 Linux Image 头布局写，U-Boot 的 booti、GRUB、QEMU 的 -kernel 都认这个格式。

你的骨架：照着 Xen 这段头部改写（去掉 EFI 部分也行，保留 "ARM\x64" magic 和几个 .quad 即可，完整写法见附录 A）。

2.2 位置无关代码与 phys-offset

问题：链接器按某个假设地址（比如 0x40200000）生成你的代码，但引导器可能把你放在任意物理地址。MMU 还没开，代码必须“放哪都能跑”。

Xen 的做法（real_start 内）：

ldr 与 adr 的区别：

  • ldr x0, =start 是伪指令：汇编器把 start 的链接时地址作为立即数放进常量池，ldr 把它读出来。这个值在链接时就固定了。
  • adr x19, start 是 PC 相对寻址：把“当前 PC 到 start 的距离”加到 PC 上，得到 start 此刻真实所在的地址。代码被搬到哪都算得对。
  • 两者之差 phys-offset 就是“引导器把我搬离了多远”。之后任何需要绝对地址的地方（比如写页表项），都用 链接地址 + phys-offset 换算。

你要学的：MMU 开启前，取地址用 adr、adrp 或 adr_l，跳转只用相对跳转（b/bl 本来就是相对的）。如果把 ldr x0, =某符号 读出的链接地址当作运行地址，在“加载地址 ≠ 链接地址”的机器上就会取指失败。这类 bug 在 QEMU 上往往测不出来，因为 QEMU 通常按链接地址加载；换到真机才暴露。

2.3 EL2 检查（check_cpu_mode）

Xen 的做法（arm64/head.S，逐字）：

  1. mrs x5, CurrentEL：读当前异常级别。CurrentEL[3:2] 是 EL 编号，低两位 RES0，所以 EL2 的读数是 0x8。0x9 是 PSTATE 里 EL2h 的模式编码（PSR_MODE_EL2h），不是 CurrentEL 的读数。
  2. ccmp x5, #PSR_MODE_EL2h, #0x4, ne 是条件比较。上一条 cmp 已经把 x5 和 PSR_MODE_EL2t（0x8）比较过；只有结果不等（ne）时，ccmp 才继续和 PSR_MODE_EL2h（0x9）比较。若条件不成立，ccmp 直接把 NZCV 设为 0x4，即 Z=1。
    • 对 CurrentEL 来说，EL2 的 0x8 已经让第一个比较相等；第二个比较针对 PSTATE 编码，在当前架构下不会命中。
    • 紧跟 b.ne 1f：两次比较都不相等（Z=0）才跳去报错。
  3. 失败时不是默默死机，而是用 earlyprintk 打两行提示再 b fail。检查失败时要能打印原因，否则只能靠猜定位问题。

你要学的：hypervisor 只能跑在 EL2（否则 HCR_EL2 等寄存器根本不存在），所以进入后第一时间确认。顺带一个工程习惯：从第一行汇编就接好 earlyprintk（往 UART 基址写字符即可，几十行代码），否则前面任何一站出错你都只能对着黑屏猜。

2.5 恒等映射与开 MMU（enable_mmu）

问题：写 SCTLR_EL2.M=1 的那一瞬间，取指立刻开始走 MMU 翻译。如果此时“下一条指令的虚拟地址”翻译不到正确的物理地址，CPU 会当场取指异常。解法是恒等映射（identity mapping） ：先建一套 VA == PA 的页表，开 MMU 后程序继续按原地址运行，之后再换成真正的虚拟地址布局。

Xen 的使能序列（arm64/mmu/head.S，节选，顺序如下）：

屏障顺序的理由：

步骤 指令 理由
1 tlbi alle2 夹在 dsb 里 清掉 TLB 里可能的陈旧翻译，保证 MMU 一开就按新页表走
2 msr TTBR0_EL2 + isb 页表基址写进去后，isb 确保后续指令看到新基址
3 dsb sy 在写 SCTLR 之前 页表是内存里的数据，必须先确保写入对所有观察者可见，否则 MMU 硬件可能读到半成品页表项
4 msr SCTLR_EL2（M 位置 1） 这一刻起 MMU 真正生效
5 isb 紧跟其后 刷掉流水线里已经预取的、按旧状态取来的指令

可以记成：​dsb​​ ** 管数据（页表写完推到底），​​isb​​ ** 管指令（流水线重新来）；两者都不能少，顺序不能换。

你要学的：先用一个 1:1 的恒等映射页表（哪怕只映射你所在的内存段），确认 MMU 开启后程序仍能正常执行，再谈虚拟地址布局。Xen 真正的虚拟内存布局（高半区映射、拆恒等映射）是在 C 里 setup_pagetables() 做的，不必在汇编里一步到位。

2.6 跳入 C 世界

MMU 开了、BSS 清零之后，Xen 做最后三步（arm64/head.S 的 real_start 尾部）：

  1. 把 DTB（设备树）物理地址放 ​​x0​​ ** 传进 C**。这是 hypervisor 与引导器之间的主要交接物：内存多大、有哪些设备、哪些中断，都在这里。
  2. 进 C 前要有一个够用的栈（Xen 用 per-CPU 的 boot stack）。C 函数会压栈，没有栈，start_xen 第一行就会出问题。

到这里，汇编部分结束。

2.7 init_traps 与陷获配置

进了 start_xen，Xen 的第一件事是 ​init_traps()​ ，而不是解析设备或建真正的页表。源码注释说明理由（arm/setup.c）：

/* Initialize traps early allow us to get backtrace when an error occurred */

先装好异常处理，后面任何一步出错才有 backtrace 可看，而不是无声死机。

五个寄存器的作用：

寄存器 作用 Xen 的设置与意图
VBAR_EL2 EL2 异常向量表基址 指向 hyp_traps_vector——16 项 × 128 字节、2KB 对齐的向量表。从此异常由你接管，不再落进引导器
MDCR_EL2 调试/性能监视陷获 全部置位：guest 不许碰调试寄存器和 PMU——既防信息泄漏，也防 guest 干扰你
HSTR_EL2 协处理器陷获 陷住实现定义的 c15 寄存器等，guest 访问即掉 EL2
CPTR_EL2 FP/SVE 陷获 默认陷住浮点：这样 guest 第一次用 FPU 时会掉进来，你才知道该保存/切换谁的 FP 上下文（惰性切换的前提）
HCR_EL2 虚拟化总开关 初始只开 AMO/FMO/IMO 三位：SError/IRQ/FIQ 全部路由到 EL2。其余位（比如陷获 WFI 的 TWI）留到每个 vCPU 创建时按需配置——最小可用原则

你要学的：Type-1 hypervisor 要在其他初始化之前接管异常与陷获配置。顺序错了的典型后果是：解析 DTB 时出现缺页或对齐错误，异常向量还指向引导器，机器直接重启，死因也拿不到。

向量表本身长这样（arm64/entry.S）：

为什么是 16 项 × 128 字节：ARM ARM 规定向量表 2KB 对齐，按“异常来源（当前 EL 用哪个 SP / 低一级 EL 是 64 还是 32 位）× 异常类型（Sync/IRQ/FIQ/SError）”排列成 4×4，每项只有 128 字节，放不下大代码，所以每项只是一条跳转到真正处理函数的 b。

guest 陷入后的完整链路是：guest_sync（汇编保存现场）→ do_trap_guest_sync(regs)（C 里读 ESR_EL2 的 EC 字段，用 switch 分发）→ 具体处理函数。这条链是后续 guest 支持的主要工作，属于“进 C 世界之后”的内容。

2.8 后续初始化顺序与依赖

start_xen 里有几十步初始化，顺序由依赖关系决定。Xen 源码里有几条明确的约束：

顺序约束 原因（Xen 源码注释的原话逻辑）
llc_coloring_init() → setup_pagetables() “Page tables must be setup after LLC coloring initialization because coloring info are required in order to create colored mappings”——页表要用缓存着色信息
IOMMU 初始化 → guest Stage-2 页表体系 guest 的 DMA 设备经 IOMMU 看到的地址空间必须与 Stage-2 一致，先建 IOMMU 再建 p2m，否则 DMA 就穿透隔离了
alternatives（指令动态补丁）放最后 所有 CPU 特性探测完成后，统一把“通用指令”补丁成“本 CPU 最优指令”；提前打会被后来的初始化覆盖

另一条贯穿全程的纪律：所有 CPU 特性与勘误表（errata）走声明式表格 + MIDR 匹配。Xen 用 MIDR_RANGE(model, min_rev, max_rev) 把“哪颗 CPU 的哪个修订版有哪个 bug、需要什么 workaround”集中登记成表，启动时按当前 CPU 的 MIDR 自动套用。这张表最好在项目初期就建好，避免散落的 if (midr == ...) 遍布代码库。

再看一个从 guest 返回前的收尾动作（entry.S）：

它利用硬件行为：解开 SError 屏蔽后，若有挂起的异步错误，异常恰好落在 ​​dsb​​ ** 和重新屏蔽之间那条孤零零的 ​​isb​​ ** 上，硬件会把 elr_el2 改写成异常返回地址。比较前后两个 ELR，不等就说明窗口里出事过——用“一条指令的窗口”把异步错误变成可检测事件。这种手法现在不用写，但能说明一个原则：读 Xen 的汇编时，几乎每个看似多余的屏障背后都有一条 ARM ARM 的硬件行为规则。

3.2.3 EL2 检查、栈和向量表

CurrentEL[3:2] 是当前异常级别。右移 2 位后：

  • 1 → EL1
  • 2 → EL2
  • 3 → EL3

只有 EL2 才能访问 HCR_EL2、VTTBR_EL2 等虚拟化寄存器，所以第一件事就是确认自己在 EL2。QEMU 命令里的 virtualization=on 才会让 CPU 从 EL2 起步；否则会打印 N 后停机。

  • SPSel=1 表示当前使用 SP_EL2，即 EL2h 模式。
  • _stack_top 指向 .bss 中 16KB 栈的栈顶，栈向下增长。
  • 必须先把栈建好，后面 C 函数和异常处理才能压栈。

VBAR_EL2 是异常向量表基址，要求 2KB 对齐。这里在开 MMU 之前就装好，原因是：如果页表有错，开 MMU 后的第一条取指就可能异常；如果这时 VBAR_EL2 还是 0，CPU 会跳到 0x200 之类的无效地址，连错误原因都看不到。

3.2.4 MAIR_EL2、TCR_EL2、SCTLR_EL2

MAIR_EL2：

0x44FF 的低 16 位定义了两个属性：

Attr 值 含义
Attr0 0xFF Normal，Inner/Outer Write-Back Write-Allocate
Attr1 0x44 Device-nGnRE

页表描述符里的 AttrIndx 会索引这两个属性。普通 RAM 用 Attr0，UART/GIC 等 MMIO 用 Attr1。

TCR_EL2：

写入值 0x0000000000023F19：

字段 值 含义
T0SZ[5:0] 25 VA 位数 = 64 - 25 = 39 位
IRGN0[9:8] 3 页表遍历 Inner Write-Back
ORGN0[11:10] 3 页表遍历 Outer Write-Back
SH0[13:12] 3 Inner Shareable
TG0[15:14] 0 4KB 粒度
PS[18:16] 2 40 位物理地址

PS=2 对应 QEMU virt 的 40 位物理地址。换平台时应像 Xen 那样读 ID_AA64MMFR0_EL1.PARange 再填，不要沿用这个固定值（见第 3 站）。

关键点：4KB 粒度 + 39 位 VA → 从 level 1 开始查表。

  • L1 每项覆盖 1GB
  • L2 每项覆盖 2MB
  • L3 每项覆盖 4KB

因此只需要一张 4KB 的 L1 表，用 1GB block 就能把低 512GB 恒等映射完。

如果按 48 位 VA 配置（T0SZ=16），首级会变成 L0。L0 表项只能是 table 描述符，不允许 block 描述符；把 L1 的 1GB/2MB block 直接填进 L0，开 MMU 后必然 translation fault。

SCTLR_EL2：

第一次写入 0x30D00800：

  • 保持 M=0（MMU 关）、C=0（D-cache 关）、I=0（I-cache 关）
  • 把架构规定为 RES1 的位先置 1，避免写 0 造成不可预测行为

等页表和 TTBR0_EL2 都准备好后：

第二次写入 0x30D01805，在 RES1 基础上打开：

位 名称 作用
0 M MMU
2 C D-cache
12 I I-cache

isb 确保后续指令看到新的系统控制状态。

3.2.5 恒等映射与开 MMU

boot_pgtable 是 4KB 对齐的 L1 表，共 512 项。每项描述 1GB：

  • entry[0] 覆盖 0x00000000–0x3FFFFFFF，映射为 Device，包括 GIC（0x08000000）、PL011 UART（0x09000000）、virtio-mmio（0x0A000000）等。
  • entry[1] 覆盖 0x40000000–0x7FFFFFFF，映射为 Normal，包括 QEMU RAM、内核镜像、页表、栈。
  • 其余项也填 Normal，覆盖未使用的地址空洞。

把未使用的地址空洞也填成 Normal 只是骨架的简化做法；真实 hypervisor 只映射实际使用的区域，让非法访问继续 fault。

描述符位域：

位域 0x701 Normal 0x705 Device 含义
[1:0] 01 01 有效 block
[4:2] 000 001 AttrIndx：0=Normal，1=Device
[7:6] 00 00 AP：读写，EL0 不可访问
[9:8] 11 11 Inner Shareable
[10] 1 1 AF（Access Flag）
[47:30] index << 30 index << 30 1GB block 的输出地址位（PA[47:30]）

这里有两个容易写错的位域：

  1. AF 必须置 1。如果 AF=0，第一次访问就会触发 Access Flag fault；只写 bit0=1 就会漏掉 AF。
  2. **AttrIndx 在 **​ ​[4:2]​ ，不是单独某一位。0x701 和 0x705 才是正确的 Normal/Device 描述符。

运行时内存布局：

页表准备好后，按顺序写 TTBR0_EL2、刷 TLB：

  • dsb sy：确保页表写入对所有观察者可见
  • isb：确保后续指令看到新的 TTBR0_EL2
  • tlbi alle2：失效 EL2 Stage-1 的全部 TLB
  • 再 dsb/isb：保证 TLB 失效完成

最后写 SCTLR_EL2 打开 M/C/I。从这一条指令开始，取指和访存都走 MMU；能打印 B 就说明整条恒等映射链路是通的。

3.2.6 进入 C 世界

AAPCS64 规定第一个参数放 x0。x22 是 callee-saved 寄存器，前面保存的 DTB 地址不会被中间的汇编破坏。bl 把返回地址写入 x30，然后跳到 C 函数。

C 代码能正常运行，说明：

  • SP_EL2 栈有效
  • 代码段、.rodata、栈所在的 RAM 都已映射
  • UART 所在的 Device 区间已映射
  • MMU 和 cache 配置没有破坏取指/访存

3.2.7 异常向量表

AArch64 向量表固定 16 项、每项 128 字节，按“异常来源 × 异常类型”排列：

偏移 来源 异常类型
0x000 Current EL，SP0 Sync / IRQ / FIQ / SError
0x200 Current EL，SPx Sync / IRQ / FIQ / SError
0x400 Lower EL，AArch64 Sync / IRQ / FIQ / SError
0x600 Lower EL，AArch32 Sync / IRQ / FIQ / SError

每组 4 项，顺序固定为 Sync、IRQ、FIQ、SError。

当前代码 SPSel=1，所以 EL2 自己的同步异常走 0x200 这一组。每个表项只有 128 字节，放不下完整处理代码，因此只放一条 b 跳到真正的处理函数。

发生异常时，硬件会设置：

  • ESR_EL2：异常类型和原因（EC/ISS）
  • FAR_EL2：出错的虚拟地址（地址异常时有效）
  • ELR_EL2：异常返回地址
  • SPSR_EL2：发生异常时的 PSTATE

向量表入口先把 kind（0=SYNC）放进 x0，exc_common 再把 ESR/FAR/ELR 放进 x1–x3，然后按 AAPCS64 调用 C 的 exc_report() 打印后停机。故意访问未映射地址时，可以看到类似：

这说明向量表、栈和 C 异常处理都是通的。

注意：当前只是诊断用异常处理，不做现场保存/恢复。以后要跑 guest，需要在 Lower EL 的表项里保存 guest 寄存器、读 ESR_EL2.EC 分发、处理 Stage-2 fault，再 eret 回去。

3.2.8 main.c：C 世界的初始化

系统寄存器写宏：

#r 把参数变成寄存器名字符串。例如：

展开成 msr VBAR_EL2, xN。

HCR_EL2：

位 名称 作用
31 RW EL1 使用 AArch64（0 则 AArch32）
5 AMO 物理 SError 路由到 EL2
4 FMO 物理 FIQ 路由到 EL2
3 IMO 物理 IRQ 路由到 EL2

这是 hypervisor 的基本配置：低异常级的中断先陷到 EL2，由 hypervisor 决定是否注入给 guest。当前还没有 guest，也没有配置 GIC，所以这些位只是“准备好”，不会有实际中断。

UART 输出：

volatile 防止编译器把连续写 UART 的操作优化掉。putc_() 直接写数据寄存器，puts_() 循环输出字符串，puthex() 把 64 位值打成 16 个十六进制字符。

这是简单的轮询输出，不检查 PL011 的 TX FIFO 是否满。QEMU 模型可以直接接受；真实 UART 通常要先读 UARTFR 的 TXFF 位，等 FIFO 有空位再写。

​hv_main()​ ：

流程：

  1. 打印 C，证明已经进入 C 世界
  2. 打印 Hello, world!
  3. 打印 QEMU 传进来的 DTB 地址
  4. 再设一次 VBAR_EL2（汇编里已经设过，重复设置无害）
  5. 配置 HCR_EL2
  6. 打印 D
  7. wfi 循环

wfi 在没有任何中断源时会停住 vCPU，QEMU 就静默下来。这是预期行为，不是卡死。

3.2.9 当前边界与下一步

这个骨架已经具备：

  • EL2 启动
  • earlyprintk
  • 恒等映射 MMU
  • D-cache / I-cache
  • 2KB 异常向量表和异常诊断
  • C 运行环境（栈、只读数据、MMIO）

但还不是完整的 Type-1 hypervisor：

  • 没有配置 Stage-2 翻译（VTCR_EL2、VTTBR_EL2）
  • 没有创建/启动 EL1 guest
  • 没有 GIC、定时器、虚拟中断注入
  • 没有保存/恢复 guest 上下文
  • 异常处理目前只打印后停机，不恢复执行
  • 没有主动清 BSS（QEMU 启动时 RAM 默认清零；真实硬件需自己清）
  • UART 输出没有检查 TX FIFO（QEMU 可用，真机建议补上）

下一步通常按这个顺序推进：配 Stage-2 页表 → 准备 guest 镜像和 DTB → 初始化 GIC → 设置 ELR_EL2/SPSR_EL2/SP_EL1 → eret 到 EL1。对应到 Xen，就是 p2m、domain、vgic 那几条线。

第四章：十个常见错误

  1. ​ldr x0, =symbol​​ ** 当运行地址用**——那是链接地址。MMU 开启前一律用 adr/adrp。QEMU 上能跑不代表真机能跑。
  2. 开 MMU 前忘了 ​​dsb sy​——MMU 硬件读到半成品页表项，症状是随机取指异常，极难调试。
  3. 写完 SCTLR 忘了 ​​isb​——流水线里预取的旧指令继续跑，表现为偶发异常。
  4. 恒等映射没映射“下一条指令” ——msr SCTLR_EL2 一生效，PC 所在 VA 必须能翻译到同一 PA。
  5. ​VBAR_EL2​​ ** 没 2KB 对齐**——写进去低位被硬件忽略，异常一来就跳到无效地址。用 .balign 2048（或 .align 11）。
  6. 进 C 前没栈——C 函数序言第一条 stp 就会写到无效内存。
  7. EL2 检查失败后静默死机——earlyprintk 先接好，把 CurrentEL 打出来再停机。
  8. TCR 的 PS 字段写死——换一颗物理地址位宽不同的芯片就会出问题。读 ID_AA64MMFR0_EL1.PARange 按实际值配置（学 Xen 的 ubfm/csel/bfi）。
  9. ​HCR_EL2​​ ** 一次开太多位**——先把 AMO/FMO/IMO 跑通，其余陷获位等 vCPU 机制有了再开；开多了 guest 一跑就掉进你没写处理的分支。
  10. 忘了 ​​msr SPSEL, #1​​ ** 前后 SP 的含义变了**——EL2t/EL2h 下 sp 指向不同的寄存器，混用会导致栈错误。

第六章：后续学习路线

跑通本手册的骨架（看到 A/B/C/D 标记）之后，可以按这个顺序扩展你的 hypervisor；每一步都有对应的 Xen 实现可以对照精读：

  1. 真正的向量表与同步异常处理：写 16 项向量表 + do_trap_sync 雏形，能在异常时打印 ESR_EL2 和 backtrace（对应 Xen entry.S + traps.c）。
  2. Stage-2 页表（p2m） ：给第一个 guest 建 VTTBR_EL2 映射（对应 Xen mmu/p2m.c，注意 break-before-make：改表项要先失效、刷 TLB、再写新值）。
  3. 创建第一个 vCPU 并 ​​eret​​ ** 进 guest**：构造初始寄存器上下文，跑一段 guest 裸机代码（对应 Xen domain.c）。
  4. hypercall 与陷入分发：实现 hvc #0 通道 + ESR.EC 的 switch 分发（对应 do_trap_guest_sync / do_trap_hypercall；其中 0xDEADBEEF 寄存器投毒和 regs->pc -= 4 抢占重放两个技巧值得留意）。
  5. 中断虚拟化：GICv3 + vGIC，LR 寄存器注入虚拟中断（对应 gic-v3.c / vgic.c）。
  6. SMCCC 与 PSCI：让 guest 能开机、关机、调用固件服务（对应 vsmc.c）。
  7. CPU errata 与 Spectre 缓解：建 MIDR 表、部署硬化向量（对应 cpuerrata.c / bpi.S）。
  8. SMP 多核启动：secondary CPU 走和 boot CPU 相同的七站，只是各自的栈与 per-CPU 数据不同（对应 smpboot.c）。

每加一步，回到 Xen 对应文件对照精读——本手册配套的《Xen-AArch64-ARMv8-A 实现深度分析》报告里有这些函数的逐行讲解和交互式调用图。
